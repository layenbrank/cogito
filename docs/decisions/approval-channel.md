# 写操作的人工审批通道：闸门在编排里，决定走邮箱（不采用接口同步等待）

> 目标：模型自己发起、会**改变别人之后能读到的东西**的工具调用（`memory_write`、`asset_visibility_write`），
> 必须经人批准才真的执行；批准、驳回、没人处理三种结局都要**确定且可追溯**，
> 且不能被 durable 的「至少一次」重投递搞乱。
> 结论：**闸门（等待 + 判定）放在 durable 编排里**，人的决定由 api 落台账后投进实例的
> **邮箱**（`enqueue_event`），编排 `select` 「邮箱消息 vs 超时定时器」二者之一。

> 这条 ADR 修正了 P9c 留下的一个说法：[`../apps/service/guide/agent-runtime.md`](../apps/service/guide/agent-runtime.md)
> 当时写「将来要接写操作，durable 的 `raise_event` 已经具备承载能力」——**能力具备，但语义不对**，
> 见 §2.2。落地在 P10a（cogito 侧审批闸门 + `agent_approval` 台账 + 审批接口），
> compute 侧只负责「申报这次调用要人批」。P10b 补上第二条落地路径——**拿审批行换写令牌**，
> 让编排不必持有能改 cogito 业务数据的凭据，见 §5。

## 0. 候选对照

| 候选                                                       | 形态                                                                                                                     | 结论                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **编排闸门 + 邮箱投递**                                    | 编排挂起等人，把待办编码进 custom status；决定经 api 落台账后投进邮箱                                                     | **采用**                                                   |
| 接口同步等待                                               | 单独一个「审批」接口，处理请求的协程里 `select` 编排状态直到人批或超时                                                     | 不采用，见 §2.1                                            |
| 编排闸门 + `raise_event`                                   | 同上，但决定用事件而不是邮箱                                                                                              | 不采用，见 §2.2（P9c 的原设想）                            |
| 待审批落 cogito 表、编排轮询表                               | api 只写一行「等审批」，编排反复读表看决定来了没有                                                                        | 不采用，见 §2.3                                            |
| 只靠 `allowed_tools` 开关（不开写工具就没有风险）           | 干脆不让 agent 写                                                                                                         | 不够：这是「全开或全关」，写工具就永远用不了，见 §2.4      |
| 把写操作做成「生成一条待办、由人另外走一个业务接口」        | agent 只提议，人自己走业务流程                                                                                            | 不采纳为**本通道**：那是产品形态的选择，不是这条链路的替代 |

## 1. 三条约束决定了后面每一条理由

| #   | 约束                                                                                                   | 出处                                                        |
| --- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 1   | 循环是 **durable 编排**：可能被换进程接着跑，任何一步都可能被重投递（至少一次）                          | `docs/decisions/durable-execution-engine.md`、`guide/agent-runtime.md` |
| 2   | **api 是台账的唯一写者**，orchestrator 不碰业务表（它只跑编排、调活动）                                  | `src/services/agent/README.md`                              |
| 3   | 人的动作发生在**无法预知**的时刻（几秒后、几小时后都可能），而且那时 api 与 orchestrator 都可能是别的进程 | 审批本身的定义                                              |

## 2. 决定性理由

### 2.1 闸门必须在编排里：它是「谁在等」的唯一权威

「这次调用还在等审批吗」这句话的判定权，属于**编排的当前状态**，不属于任何一张表：
超时是编排的定时器到点了，批准是编排从邮箱里取到了决定。接口拿这个判断只能靠「读一个副本」。

同步等待的接口看起来更简单（一个请求、一次返回），代价是：

- 把一次审批的寿命绑在一个 HTTP 连接上（最长 30 分钟）。连接断掉、负载均衡换机、滚动发布，
  都会让「人已经批了」和「请求早就断了」同时发生——决定就此丢失，而**丢失的决定是不可恢复的**。
- 它没有地方落「决定」这件事：要么把决定存在接口进程的内存里（进程一死就没了），
  要么还是得落台账——那就已经回到本条方案的形状，只是多背了一个长连接。
- 「超时」在同步接口里是 `SELECT` 自己发明的，在编排里是 `schedule_timer` 定的。
  两个时钟一旦不一致，就会出现「接口报超时、编排还在等」或者反过来的窗口。

所以这里是**编排持闸门、api 只送决定**：闸门是编排的路径（执行 / 不执行），
决定的记录是业务数据（谁的、什么时候、什么理由）。两者分开，各自只需要一个写者。

### 2.2 邮箱而不是事件：到达时间不可预知

`durable` 有两条投递通道，差别是**匹配语义**（`crates/durable/src/client.rs` 的原文）：

- `raise_event`：按**位置**配对——订阅必须已经绑上，早到的投递没人接，就丢了；
- `enqueue_event`：投进**邮箱**，早到就存着，谁先订阅给谁，跨 `continue_as_new` 存活。

审批决定正是「什么时候来无法预知、来了必须被接住」的通知：编排在挂起的那一刻才订阅，
而人可能在编排还没走到订阅点时就点了批准（前端拿到 `pendingApproval` 与编排真正开始
`dequeue_event` 之间永远有一个窗口）。走 `raise_event` 的话，这个窗口里的决定会**静默消失**——
接口回了 200、台账里也记着，任务却一直等到超时。这是 P9c 之后改用邮箱的唯一原因，也是
这条 ADR 存在的意义。

### 2.3 待审批不落表：副本会与权威不一致

看起来更「稳妥」的做法是 api 写一行 `PENDING`、编排轮询表。它的问题不是性能，是**引入了第二个真相**：

- 编排超时了但那一行还没被清掉 → 人批了一个已经作废的调用，接口还得再问一次编排才知道；
- 编排已经执行完了但那一行还没被清掉 → 人批了个「已经过去」的调用；
- 每个这样的中间态都要清理，而「清理」在至少一次的世界里永远漏得掉。

所以出参里的 `pendingApproval` 是**从编排的进度串投影出来的只读视图**（
`orchestrations/agent.rs::pending_approval`），不落库；落库的是**人的决定**，
只有人能写、只有一次（改判是业务冲突，409）。副作用是「待审批」这件事在
`agent_task` 表里查不到——这是取舍，不是遗漏。

### 2.4 只有开关没有审批，等于把这个能力关掉

`allowed_tools` 是「这套部署允不允许 agent 写」的开关，粒度是**部署**。审批是「这一次写要不要人点头」，
粒度是**调用**。两者解决的不是同一个问题：

- 只有开关：想用写工具就必须无条件信任模型，模型每写一条都进同租户的长期记忆，投毒一次影响此后每次召回。
- 只有审批没有开关：每次任务都可能弹出一堆待办，运维面被淹没（所以 `memory_write` **默认不在** `allowed_tools` 里）。

两者都留：开关决定「这个部署用不用写工具」，审批决定「这一次写行不行」。这也是为什么
`memory_write` 的默认值是「关闭，开着也要每次批」——默认部署一条审批都不会产生，开了之后每一条都要人看。

## 3. 代价与后果

| 代价                                                         | 我们接受它的理由                                                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 任务可能停在一个「等人」的状态上（最长 `approval_ttl_secs`） | 这正是要的语义；上限由配置控制，且必须明显小于等待者的预算（见下）                                      |
| 多了一张表（`agent_approval`）与一条路由                     | 落台账是审计要求：**谁**在**什么时候**批了**哪一次**调用、理由是什么，只靠编排快照答不出来             |
| `EXPIRED` 只出现在任务快照里、不在审批台账里                 | 台账记的是**人做的决定**，超时没有人参与。把它写成一行会让人以为「有个人超时了」                        |
| 编排要会解析 `approvalID`、忽略「不属于本次」的消息           | 决定的到达顺序不可控（重复提交、旧消息），忽略比吃掉安全：属于本次的那条迟早会到                        |
| 审批时长与等待者预算必须分档：`approval_ttl_secs`（默认 1800s，下限 60s）**必须明显小于** `dispatch.rs` 的 `WAIT_BUDGET`（3600s） | 否则任务先被等待者判失败，人在批准时实例已经没人接了——这个下限由 `cogito` 侧测试钉住                   |

## 4. 落地与门禁

落地形状（P10a）：

- 模型要写 → compute 在工具结果里**申报** `awaitingApproval=true`（占位结果**不进历史**，
  免得模型把「没执行」当既成事实）；
- 编排 `approve_and_execute`：把待办编进 custom status（`step:{n}/{max} tools:{k} approval:{JSON}`）→
  `select(邮箱消息, 超时定时器)` → 取出决定后立刻把进度串**改回**纯进度（别让运维看到一个已经批过的待办）；
- 批准 → `execute_approved`（**唯一**执行受保护工具的路径）：请求体用**人批过的那份参数原文**，
  幂等键 `{instance}:approval:{approvalID}`，允许重投递；
- 驳回 / 超时 → 合成一个「没执行」的工具结果（含理由）喂回模型，任务继续：**模型要知道为什么不行**；
- 人的动作 → `POST /api/v1/agent/tasks/{id}/approvals/{approvalID}`：落 `agent_approval` → 提交 →
  投邮箱 → 标记已投递。投递失败如实回 503，此时台账里 `appliedAt` 仍为空，重复提交同方向的决定就是**补投**。

门禁：

- `apps/service/tests/agent_approval.rs`（4 个用例，进 CI）：批准真的执行 / 驳回不执行并把理由喂回模型 /
  没人处理到点作废 / 决定的四道闸（跨租户、待办状态、决定词表、不属于本次的消息被忽略）。
- `apps/service/crates/agent` 单测钉住状态机（`EXPIRED` 不是人能给的、改判是冲突）。

## 5. 第二种落地：拿审批换「写令牌」（P10b）

P10a 走的是「编排拿到决定后**自己**执行」——适用 `memory_write`（写的是 compute 自己的存储，编排有凭据）。
`asset_visibility_write`（改 cogito 里的资产可见性）不能照抄：叶子服务不该持有能改 cogito 业务数据的长期凭据，
所以改成**审批行本身当凭据**去换一枚短期令牌。

三条不变量：

1. **令牌即能力**：`POST /api/v1/service/token` 带 `approvalID`，cogito 当场回读 `agent_approval`，
   确认「存在 / `APPROVED` / 批的是这个资产 / 批准人是资产创建者」后，把审批原文里的
   `visibility`、`viewers` 解析并钉进令牌载荷。写端点因此**没有请求体**——调用方没有可以撒谎的地方。
   代价是令牌不可回收，只能靠短有效期（`ttlSecs`）兜着；判定全在签发那刻做完，写端点只重放。
2. **审批人必须是资产创建者**：`asset` 的行级策略里 `WITH CHECK` 只认 `"creator" = app_current_user_id()`。
   所以这不是额外加的规矩，而是唯一能写成功的组合。
3. **写以批准人身份落地**：写路径进的是**该用户的**作用域，而不是租户作用域——否则 `WITH CHECK` 直接拒。
   换句话说，「能不能写这个资产」的最终判定仍然只有数据库一处，接口层的审批校验只是**提前失败**。

### 路径为什么落在服务面（`/api/v1/service/assets/{id}/visibility`）

早先的推进记录里记的是用户面的 `/api/v1/assets/{assetID}/visibility`，实现时改到服务面，理由三条：

- **调用方是 compute，不是用户会话**。放用户面就得让叶子服务持有用户 JWT——把用户的长期凭据塞进
  计算车间，正是服务身份面存在的意义（见 [`architecture-capabilities.md`](../apps/service/guide/architecture-capabilities.md)）。
  而 P10b 的授权输入（真凭实据的审批原文 + 批准人）在签发那刻就齐了，端点连请求体都没有，
  它本来就是服务面的形状。
- **与读内容同族**：`GET /service/assets/{id}/content` 已经在这里，可见性判定共用同一段逻辑
  （`service_asset_parts`），读写走同一个 scope 与同一套 403/404 口径，不会出现「读一套写法、写另一套写法」。
- **不产生第二套语义**：用户面根本没有「改可见性」接口（可见性只在 `prepare` 设定、绑定头像时提升为
  `PUBLIC`），所以放服务面也不需要回答「用户面那套怎么对齐」。

失败面：审批凭据不合规一律 `500509`（HTTP 403），原因只进日志——跨租户不该能从响应里探测出
「某条审批存在吗」。只有请求体少字段（`200003`）与资产不存在 / 看不见（`500204`，HTTP 404）例外。

## 6. 事实核对
