# RAG 索引与检索

路由前缀：`/api/v1/rag`

## 概述

把一份**已完成上传的资产**切块、算嵌入、写进向量索引，供之后检索。索引一份文档要跑抽取、
分批嵌入、落索引三步，是分钟级的长任务，所以它跟 agent 一样只暴露「起任务 / 查任务」两个接口，
真正的流程在编排里（[`orchestrations/rag.rs`](../../orchestrations/rag.rs)），由 orchestrator 进程驱动。

| 能力     | 说明                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 起任务   | 校验资产可索引 → 落一条 `RUNNING` 台账行 → 提交 → 起 `rag.index-asset` 实例   |
| 查任务   | 读台账；还在跑就顺带问一次编排当前进度，问不到也不影响返回                  |
| 检索     | `POST /search` → `compute /internal/v1/rag/search`（只读，无台账）            |
| 收尾     | 编排进终态时把结果 / 失败原因写回台账（等待者或读路径触发）                  |
| 读时修复 | 台账显示 `RUNNING` 但编排里实例已不存在时，按行龄判定是否收敛成失败         |

**与 agent 域的差别**（同一套模式的两次落地，先看 [agent/README.md](../agent/README.md) 再看这里）：

- 没有 `steps`。索引的批数随资产大小变，出参里写一个「第几批 / 共几批」只会误导调用方；
  过程量走 `progress`（编排原样自报的 `chunked:48` / `embedded:32` / `indexed`）。
- 多一条**并发闸门**：同一资产同时只允许一个在跑的任务（见下）。
- 多一步**资产可索引性校验**：索引的输入是一份资产，不是一段文字。

## 数据所有权

| 表               | 归属   | 说明                                                     |
| ---------------- | ------ | -------------------------------------------------------- |
| `rag_index_task` | 本模块 | 索引任务台账：资产、状态、编排实例名、结果、失败原因      |

切块、向量与索引本身归 `compute`（那里是派生数据、可从源重建）。cogito 这边只有「谁在什么时候
索引了哪份资产、跑成什么样」这一行记录。

`asset` **不是本模块的表**：起任务时按 id 读一次（在租户作用域内，凭 RLS 保证只看得到本租户），
不写它、不 Join 它。这是「一模块一表」规则的正常形态：跨域只读别人的行，不碰它的写路径。

## 谁在跑索引

```
POST /api/v1/rag/index-tasks
        │  ① 校验资产 + 建行（本请求事务）
        ▼
   commit ──► ② Client::start("rag-index-{task_id}", "rag.index-asset", input)
        │
        │      orchestrator 进程：rag.index-asset
        │        ├─ rag.chunk-object  → compute POST /internal/v1/assets/{assetID}/chunks
        │        ├─ rag.embed-batch   → compute POST /internal/v1/assets/{assetID}/embeddings（一批一个活动）
        │        └─ rag.upsert-index  → compute PUT  /internal/v1/assets/{assetID}/index
        │              （每一次模型调用走 cogito 网关 scope=embeddings，配额/计量/审计自动生效）
        ▼
   ③ 收尾：等待者轮询 Client::status，或下一次 GET 读时发现终态 → 写回台账
```

分块与嵌入**已完成的步骤不会重跑**：编排每步的幂等键是 `{instance}:chunk` / `{instance}:embed:{from}-{to}` /
`{instance}:index`，杀掉进程重启后只补当前批（故障注入测试 [rag_fault_injection.rs](../../tests/rag_fault_injection.rs) 就是这条）。

## 顺序铁律：先落台账，再起实例

与 agent 域完全相同，理由也一样（写在 [service.rs](service.rs) 的模块头）。唯一补充的是这里的
**失败方向**：索引烧的是嵌入算力，一份几万块的文档重跑一次不是免费的——所以「有台账、无实例」
这种可收拾的残留比「有实例、无台账」重要得多。

## 并发闸门：同一资产只允许一个在跑的任务

两道防线，缺一不可：

1. **先查**（`running_for`）：命中就直接 409，并把已有任务的 ID 放进 `details.taskID`，
   调用方拿它去查即可，不用重试。
2. **部分唯一索引**（`uidx_rag_index_task_running ... WHERE status = 'RUNNING'`）：两个请求同时
   通过第 1 步时，第二个会在写库时撞唯一键，退化成不带 `details` 的 409。

为什么不能只做第 2 步：撞唯一键会让整个事务进入 aborted 状态，**同一个事务里回查不到那条冲突行**，
所以想给调用方一个有用的 `taskID` 就只能在写之前先查一次。为什么不能只做第 1 步：两个请求之间
有窗口，纯靠应用层检查等于没有闸门。

重跑一份资产是**安全**的：索引是派生数据，成功的任务会覆盖旧索引，不需要先删除。

## 资产可索引性

起任务在写台账**之前**就把这些判完，所以坏入参留下的是**零**台账行：

| 情况                                       | 结果              |
| ------------------------------------------ | ----------------- |
| `assetID` 不是 UUID                        | `500602`（404）   |
| 该 id 在本租户内不存在                     | `500602`（404）   |
| 资产已归档（`archivedAt` 非空）            | `500602`（404）   |
| 资产状态不是 `COMPLETED`                   | `500603`（422）   |

「id 非法」与「不是我的资产」合并成同一个 404，归档也并进去：分开会让调用方能拿状态码探测别的
租户有没有某个 id，或者探测某份资产是不是被归档了。归档资产在用户侧本来就看不见（列表查询过滤
`archivedAt is null`），说「不存在」与事实一致。

未完成上传的资产是 422 而不是 404：它是**看得见但不能用**，调用方该做的是等上传完成，
而不是以为自己填错了 id。下游 compute 也取不到未完成资产的内容，提前拒绝能省掉一条注定失败的任务。

## 路由一览

| 方法 | 路径                               | 鉴权                         | 说明                       |
| ---- | ---------------------------------- | ---------------------------- | -------------------------- |
| POST | `/api/v1/rag/index-tasks`          | JWT + `X-Tenant-ID` 租户成员 | 起任务，返回 `RUNNING` 台账 |
| GET  | `/api/v1/rag/index-tasks/{id}`     | JWT + `X-Tenant-ID` 租户成员 | 查任务进度与结果           |
| POST | `/api/v1/rag/search`               | JWT + `X-Tenant-ID` 租户成员 | 检索（只读，无台账）       |

## 鉴权说明

- 中间件 `Auth::isRequired()` 挂在整个 scope 上，未登录直接 401 类。
- **租户来自 `X-Tenant-ID` 请求头，且必填**，不降级到账号作用域：资产按租户隔离，猜错租户会把
  A 的文档索引进 B 的检索面。缺头 `200001`、格式错 `200007`。
- 权限**直接复用资产的写 / 读权限**（`Asset/Write` 起任务、`Asset/Read` 查任务）：索引是「对这份
  资产的加工」，能改资产的人才能索引它，能看资产的人才能看它的进度。为它单开一对权限只会让权限
  种子多两份没人会去调的配置，而且**权限种子零改动**。
- 查任务时 id 非法与「不是我的任务」回**同一个 404**（`500601`）。

## 错误码

| 码       | HTTP | 场景                                     |
| -------- | ---- | ---------------------------------------- |
| `200001` | 400  | 缺少 `X-Tenant-ID` 请求头                 |
| `200007` | 400  | `X-Tenant-ID` 格式无效                   |
| `300007` | 403  | 非该租户成员                             |
| `500601` | 404  | 索引任务不存在 / 不属于当前租户 / id 非法 |
| `500602` | 404  | 资产不存在 / 不属于当前租户 / 已归档      |
| `500603` | 422  | 资产尚未完成上传                         |
| `500604` | 409  | 该资产已有正在运行的索引任务             |
| `500605` | 503  | 编排运行时未接通，或实例启动失败         |
| `500606` | 400  | 检索词为空                               |
| `500607` | 503  | compute 未接通或检索失败（可重试）        |

`500605` 意味着「这次确实没跑起来」，台账那一行会被落成失败，可直接重试。**内部原因（连接串、
运行时错误）只进日志与台账，不进响应**。编排运行时是可选接线：没配置时进程照常起，只是起任务回
503、查任务只返回台账原样。

## 出参
`status` 是台账状态：`RUNNING` / `SUCCEEDED` / `FAILED`。

- `progress`：编排自报的进度串（`chunked:48` / `embedded:32` / `indexed`），**原样透传不解析**，
  只有还在跑且问得到时才有。
- `result`：编排输出快照——`chunkSetID` / `chunkCount` / `batches` / `dimensions` / `indexed` /
  `collection`，成功后才有。`chunkSetID` 是拿这份资产的向量去检索时的入口。
- `error`：失败原因，已翻译成面向调用方的说法（`infrastructure` / `configuration` /
  `application` / `poison` → 中文说明）。

## 检索（`POST /search`）

一次只读调用：`{ query, topK?, assetIDs? }` → `{ hits: [{ assetID, ordinal, score, text }] }`。

- **模型由服务端定**（`compute.embed_model`）：必须与索引时用的那个一致，不同向量空间的距离
  没有可比性，所以调用方不能指定。客户端传错只会拿到空结果，把排查方向引到「索引没建好」上。
- **`assetIDs` 是收窄**：省略 = 本租户全部；空数组 = 没有可查的资产（返回空列表，
  不退化成全租户——否则客户端会检索到自己已经删掉的文档）。
- **空列表不是错误**：没有已索引内容、或没有相近块，都是正常结果。
- 服务端**不做融合**：本地 FTS 与云端向量的 RRF 在客户端做（它同时拿得到两路结果）。
- 失败只分两类：参数问题 `200003`（不重试），下游暂时不行 `500607`（可重试）。

## 排查手册

把索引的进度与 `/internal/v1/...` 的幂等键对起来看，能一眼分出三类问题：

```
# 台账里有这一行吗（行在就会显示，与运行时是否活着无关）
curl -s "$API/api/v1/rag/index-tasks/{taskID}" -H "Authorization: Bearer $TOKEN" -H "X-Tenant-ID: $TENANT"
# → RUNNING 且 progress 长期不动：查编排实例是不是被卡住了（orchestrator 日志 / durable 实例状态）
# → RUNNING 但编排里没这个实例、且行龄超过 5 分钟：编排实例真丢了，读路径会把它收敛成 FAILED
# → FAILED 且 error 含「编排配置错误」：看编排注册时的参数（模型 / 批大小），不是资产的问题
```

| 现象                                        | 常见原因                                                         |
| ------------------------------------------- | ---------------------------------------------------------------- |
| 起任务回 `500604` 并带 `taskID`             | 上一次没跑完；查那个任务，不要重试起新的                         |
| 起任务回 `500603`                           | 资产还在分片上传中，等 `COMPLETED` 再来                          |
| `progress` 停在 `embedded:k` 很久           | 单批嵌入慢或卡在网关重试；看 compute 与 gateway 日志            |
| 终态 `FAILED` 且 `error` 含「下游 500」     | compute / 上游嵌入服务的问题，可重跑同一资产（旧索引会被覆盖） |
