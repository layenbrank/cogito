# Agent

路由前缀：`/api/v1/agent`

## 概述

租户级**自治 agent 任务**：给一个目标，它在服务端跑完多轮「模型思考 → 调工具 → 再思考」，最后把答案与过程落进台账。无人在环、可以跑很久，所以它是个**长任务**，不是一次请求——这也是本模块存在的理由：接口只负责「起任务」和「查任务」，真正的循环在编排里（[`orchestrations/agent.rs`](../../orchestrations/agent.rs)），由 orchestrator 进程驱动。

| 能力     | 说明                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 起任务   | 校验入参 → 落一条 `RUNNING` 台账行 → 提交 → 起 `agent.run` 实例，立刻返回    |
| 查任务   | 读台账；还在跑就顺带问一次编排当前进度，问不到也不影响返回                  |
| 收尾     | 编排进入终态时把结果 / 步数 / 失败原因写回台账（等待者或读路径触发）        |
| 读时修复 | 台账显示 `RUNNING` 但编排里实例已不存在时，按行龄判定是否收敛成失败         |
| 审批     | 写工具的一次调用要人先批：决定落 `agent_approval` 台账，再投递给编排；批过的台账行同时是服务面换写令牌的凭据 |

## 数据所有权

| 表               | 归属   | 说明                                                             |
| ---------------- | ------ | ---------------------------------------------------------------- |
| `agent_task`     | 本模块 | 任务台账：目标、模型、轮次上限、工具白名单、状态、步数、结果、失败原因 |
| `agent_approval` | 本模块 | 审批台账：**人做的决定**（谁在什么时候批/驳了哪一次调用、理由）   |

**不再有第二张表**：agent 的长期记忆与向量归 `compute`（见 [compute README](../../../../compute/README.md)），cogito 这边只留「谁在什么时候要了什么、跑成什么样」这一行记录。台账因此**不可从源重建**，需要跟业务表一起备份。

审批台账同理只记**决定**：`EXPIRED` 不是人做的决定，不落表；一次调用批过了但编排还没接住（`appliedAt IS NULL`）会在下次同方向提交时被补投，而不是再写一行。

## 谁在跑这个循环

```
POST /api/v1/agent/tasks
        │  ① 建行（本请求事务）
        ▼
   commit ──► ② Client::start("agent-{task_id}", "agent.run", input)
        │
        │      orchestrator 进程：agent.run 循环
        │        └─ agent.step → POST compute /internal/v1/agents/steps
        │              （每步最后一次模型调用走 cogito 网关 scope=chat，配额/计量/审计自动生效）
        ▼
   ③ 收尾：等待者轮询 Client::status，或下一次 GET 读时发现终态 → 写回台账
```

三段的分工是有意拆开的：

- **api 进程**是台账的**唯一写者**。orchestrator 零改动——它跑编排、调活动，不碰台账。
- **等待者**（[`dispatch.rs`](dispatch.rs) 的 `spawn_waiter`）挂在起任务那次响应的进程里，指数退避（1s → 15s）轮询，最长一小时；它只是个**加速器**，不是正确性的必需件。
- **读路径**是兜底：任何一次 `GET` 发现编排已经终态就顺手收尾。所以等待者随进程重启消失也没关系——最坏是那行多显示一会儿 `RUNNING`，下次查询就补上了。

顺带说一句为什么不用 `Client::wait`：`wait` 在实例查不到时**立刻返回**，退避逻辑在它手上就变成了热循环。所以这里自己轮询 `status`，把「还在跑」当成正常情况对待。

## 顺序铁律：先落台账，再起实例

两步之间崩溃在任何一边都会留下缺口，只能选一种：

| 顺序                     | 崩溃后的残留                                       | 能不能收拾               |
| ------------------------ | -------------------------------------------------- | ------------------------ |
| 先起实例，再写台账       | **看不见的工作**：编排在跑、烧配额、调工具，没有任何记录指向它 | 不能，谁都查不到、收不了尾 |
| 先写台账，再起实例（现用） | 有台账、无实例                                     | 能，读路径按行龄判失败   |

所以是「建行 → `commit` → 起实例」，并且 `commit` 在业务层之外也**不能省**：网络调用不许在事务里发（连接与行锁会被一路占住）。

代价是会出现「台账 `RUNNING`、编排里根本没这个实例」。这类情况的判定只能靠**行龄**（`INSTANCE_ABSENT_GRACE = 300s`）：编排 schema 被清空或库被重建时状态同样会变成 `NotFound`，只有「这行多久之前建的」能区分「刚起还没被领走」和「早就没了」。宽限期内保持 `RUNNING`，超过就收敛成失败——**代价是实例真丢了时最多多显示 5 分钟 `RUNNING`**。

## 路由一览

| 方法 | 路径                                                | 鉴权                         | 说明                       |
| ---- | --------------------------------------------------- | ---------------------------- | -------------------------- |
| POST | `/api/v1/agent/tasks`                               | JWT + `X-Tenant-ID` 租户成员 | 起任务，返回 `RUNNING` 台账 |
| GET  | `/api/v1/agent/tasks/{id}`                          | JWT + `X-Tenant-ID` 租户成员 | 查任务进度与结果           |
| POST | `/api/v1/agent/tasks/{id}/approvals/{approvalID}`   | JWT + `X-Tenant-ID` 租户成员 | 批 / 驳一次待审批的工具调用 |

## 鉴权说明

- 中间件 `Auth::isRequired()` 挂在整个 scope 上，未登录直接 401 类。
- **租户来自 `X-Tenant-ID` 请求头，且必填**（沿用 `gateway` 的约定）。与 gateway 的区别是这里**不降级到账号作用域**：agent 任务属于「哪个租户的知识」，没有账号级的落脚点，与其猜一个不如直接拒。
  - 缺头 → `200001`（缺少参数）
  - 头在但格式错 → `200007`（请求头无效）
  - 两者分开报，是因为一个是漏了参数、一个是写错了值，混成一句会让人反复检查一个其实没写错的地方。
- 进入作用域后 `TenantCtx::enter` 完成成员关系判定：非成员/租户不存在即 403 类（`300007`），不会进到业务层。
- 写与读是两个权限（`AgentTask/Write`、`AgentTask/Read`），租户内**任何有效成员**（含 MEMBER）两者都有。分开是为了将来把「谁能烧配额」收紧成 ADMIN 而不动读路径。审批**复用 `AgentTask/Write`**：能起写工具任务的人才是该批这次调用的人，不为它单独开一个权限。
- 查任务时 id 非法与「不是我的任务」回**同一个 404**（`500501`）：分开会让调用方能拿它探测别的租户有没有某个 id。

## 入参规则

| 字段        | 规则                                                                              |
| ----------- | --------------------------------------------------------------------------------- |
| `objective` | 必填，trim 后非空，≤ 4000 字符（超限是「别把整篇文档粘进来」，不是业务规则）        |
| `maxSteps`  | 可选，缺省 = 部署上限 `agent.max_steps`；给了就必须落在 `1..=上限`，**只能往小收** |
| `tools`     | 可选，缺省 = 部署白名单 `agent.allowed_tools` 全给；给了必须是它的**子集**（去重、保序）；**空数组合法且有意义**——意思是「不给工具，直接给结论」 |
| `model`     | **不可指定**。模型 = 部署配置 `agent.chat_model`，调用方挑不了                            |

工具名用**下划线**（`knowledge_search`），跟能力名的点号（`rag.search`）不是一回事——OpenAI 的函数名规则不允许点号。

## 写工具的审批通道

写工具（`memory_write`，以及走服务面写令牌的 `asset_visibility_write`）的每次调用都**先等人批**：模型说要写，编排不直接执行，而是把这次调用挂起来等人。

```text
编排                                     api                       人
  │  ① 挂起：custom status = 进度串 + " approval:" + 待办 JSON
  │  ② select(邮箱消息, 超时定时器)                                  │
  │                              ◄── ③ POST .../approvals/{id} ──────┤
  │  ④ 收到决定 ──► 执行（APPROVED）/ 合成「没执行」结果（REJECTED）  │
  │  ⑤ 超时先到 ──► 同样合成结果（工具不执行）                        │
```

三条要点：

- **闸门在编排里，不在接口里**。「谁批的」是业务数据（落台账），但「批了之后要不要真的执行」是编排的路径——接口只负责把决定送到编排的邮箱，送不到就回 503。这样「编排进程死了、决定还在路上」不会变成一次静默的未执行。
- **投递走邮箱（`enqueue_event`）而不是事件（`raise_event`）**：决定的到达时间无法预知（人几秒钟前批、几小时后批都可能），而事件按位置配对——编排没订阅上时投递就没人接。邮箱是缓冲的，早到就存着，谁先订阅给谁。两条通道语义不同，不能互换。
- **超时不是人能给的**：到点没人处理，由编排按超时作废这次调用，理由是「编排的时钟」而不是「某人的决定」，所以 `EXPIRED` 在请求体里是非法的（`500508`），也不会出现在审批台账里。

等待时长是部署配置 `agent.approval_ttl_secs`（默认 1800s，下限 60s），见 [`guide/configuration.md`](../../../guide/configuration.md)。
**它必须明显小于等待者的预算**（`dispatch.rs` 的 3600s）：否则任务会先被等待者判失败，人在批准时实例已经没人接了。

决定只管**当前正在等的那一次**（`approvalID` 是 `{taskID}:{step}:{下标}`）：别的 id 一律 `500506`，编排那边也会忽略不属于本次审批的消息（不会误吃）。人重复点提交是安全的：决定以第一次落台账的为准，编排按第一次到的走；重复提交可能回 `applied=false`（这次只是把已有决定重投一遍），也可能已经是「不在等审批」而回 `500506`。

### 台账的第二位读者：服务面的写令牌

上面这条通道解决的是「编排怎么知道人可以走了」。还有一条反向的路：**已经批过的那条审批，本身可以当凭据用**。

编排换成 `asset_visibility_write` 这类「改库」工具时，不自带能力去写，而是拿 `approvalID` 回打
`POST /api/v1/service/token`；cogito 当场回读本模块的台账，确认「这条审批存在、`APPROVED`、参数与目标资产对得上、
而且是资产创建者亲手批的」之后，才把审批原文里的参数钉进一枚短期令牌，由 compute 用它去写
（详见 [`gateway/README.md`](../gateway/README.md#写令牌scope--asset-write把人批过的参数当唯一输入)）。

两点值得记在台账这一侧：

- **参数只解析一次，且在签发那刻**：审批原文（`arguments`）是自由文本 JSON，谁都不知道里面写了什么形状；
  「成不成形」必须在签令牌时判完（不成形即 `500509`），否则失败会晚到写端点，甚至写成半个状态。
- **台账因此是权威凭据源**：审批行不能被改写（`decision` 一旦落表就是最终值），所以「一枚令牌里钉的参数」
  与「人当时看见的参数」永远一致。这也是为什么决定是追加式的，不提供「改批一次」的接口。

## 错误码

| 码       | HTTP | 场景                                   |
| -------- | ---- | -------------------------------------- |
| `200001` | 400  | 缺少 `X-Tenant-ID` 请求头               |
| `200007` | 400  | `X-Tenant-ID` 格式无效                 |
| `300007` | 403  | 非该租户成员                           |
| `500501` | 404  | 任务不存在 / 不属于当前租户 / id 非法   |
| `500502` | 422  | 任务目标为空或超长                     |
| `500504` | 422  | 轮次上限越界                           |
| `500505` | 422  | 工具不在部署白名单内                   |
| `500503` | 503  | 编排运行时未接通，或实例启动失败       |
| `500506` | 409  | 这次调用没有在等待审批（已批过、已超时，或任务已结束） |
| `500507` | 409  | 这次调用已经有人批过了                 |
| `500508` | 422  | 审批决定不合法（只能是 `APPROVED` / `REJECTED`） |
| `500509` | 403  | 审批凭据不合规：拿一条审批去换「改资产可见性」的服务令牌时，这条审批不是「已批准」/ 批的不是这个资产 / 批准人不是资产创建者 / 审批原文里的参数不成形（非法可见性、名单含非用户 id、非 `RESTRICTED` 却带名单）。原因只进日志——跨租户不该能从这里探测出某条审批存不存在 |

`500503` 意味着「这次确实没跑起来」，台账那一行会被落成失败。**内部原因（连接串、运行时错误）只进日志与台账，不进响应**——响应只留「可重试」这一条信息。

编排运行时（`durable`）是**可选接线**：没配置时进程照常起，只是本域的两个接口会回 503 / 只返回台账原样。这样「查得到自己起过的任务」这件事不依赖编排运行时活着。

## 出参

`status` 是台账状态：`RUNNING` / `SUCCEEDED` / `FAILED`。

- `steps`：还在跑时取编排自报的进度（不写库），终态时取台账值。
- `progress`：编排自报的进度串，只有还在跑且问得到时才有。
- `pendingApproval`：当前正等着人批的那次调用（`approvalID` / `step` / `tool` / `arguments` / `expiresAt`），没有待办时为 `null`。**只在响应里，不落台账**——待审批是编排的瞬时状态（可能几秒后就超时），落库只会多出一行要清理的中间态；人批的时候才写台账。
- `finished`：模型是否给出了终答（而不是撞到轮次上限）。
- `result`：编排的原始输出（含 `answer` / `toolCalls` 计数），形状由编排契约决定，这里原样透传。
- `error`：失败原因，已翻译成面向调用方的说法（`infrastructure` / `configuration` / `application` / `poison` → 中文说明）。
