# 计划/目标持久化改造 —— 对照 VS Code Chat 实现的修订方案

## 概述

计划模式与目标模式当前都采用「每次渲染时重新计算、结果不保存」的做法：右栏计划由 `findPlanDraft()` 从**最后一条 assistant 正文**中解析，因此任何后续对话都会让计划消失；`GoalRun` 存放在模块级 `Map` 中，刷新后即丢失，审批档恢复表也只在内存里。本方案把两者改为 **thread 级持久化档案**：在 Tauri Store 的 `agent.json` 中新增 `planByThread` / `goalByThread`，由常驻的 recorder 在正文变化时写入计划快照与状态（`draft / running / done / interrupted / outdated`），右栏与目标控制条统一读取档案，而不是重新计算正文；`plan-file.ts` 补齐 `list/read`，使已保存到 `.cogito/plans/*.md` 的计划可以被识别，并且仍能一键执行。同时修掉审查出的 11 条目标模式缺陷（`stopGoalRun(null)` 崩溃、objective 截断、模式写入与发送竞态、插话被误当目标轮次、排队消息抢占轮次等）。影响面：`features/persist`、`features/agent/{plan-draft,plan-file,plan-store,goal-run,mode,approval}`、`views/agent/chat/{chat.tsx,components/aside*,composer-footer}`，不动 goose 侧协议。

## 现状与问题

**计划丢失（根因在解析层，不在 UI 层）**

- `apps/client/src/features/agent/plan-draft.ts:89` 的 `findLastAssistantText()` 从后往前只取**最后一条** assistant 的非空正文；`:234` 的 `findPlanDraft()` 直接拿它当 `body`，再从里面抽 `steps`。用户下一轮只要问一句「这个函数在哪」，最后一条正文变成问答，`findPlanDraft()` 立刻返回 `null`，右栏计划页签清空。
- `apps/client/src/features/agent/plan.ts` 的 `findLatestPlan()` 只认 goose ACP 的 `plan` data part（模型调 todo 工具才会产生）。计划模式的 Markdown 计划**从不产生该 part**，所以 `PlanAutoOpen` 里的 `planTotal` 恒为 0，既不自动展开右栏，也救不回正在展示的计划。
- `views/agent/chat/components/aside-plan.tsx:38` 的 `findPlanDigest()` / `:48` 的 `AsidePlan` 同样是「消息变了就重算」；`views/agent/chat/components/aside-busy.tsx` 的 `PlanDraftBlock` 亦然。两处都只处理正文的**瞬态**，没有任何「这份计划是什么状态」「是否已执行完」的位置。
- `aside-plan.tsx` 底部的「保存 / 复制 / 开始执行 / 目标推进」整块被 `props.isPlanMode` 包住 —— 计划出来以后只要一切到 agent 模式，按钮就消失，用户必须先切回计划模式。
- `apps/client/src/features/agent/plan-file.ts:77` 的 `savePlanToWorkspace()` 只写不读：全文件只有 `findPlanSlug / yamlScalar / buildPlanMarkdown / savePlanToWorkspace` 四个函数，没有 `list`、没有 `read`。已保存的计划文件因此**无法回读、无法一键执行**，且文件名带时间戳（`<slug>-<timestamp>.md`），反复保存会堆积成多个文件。

**目标状态丢失 + 交互缺陷**

- `apps/client/src/features/agent/goal-run.ts` 全文 280 行，`runs`（第 84 行附近）与 `approvalToRestore`（第 116 行附近）都是模块级 `Map`：刷新/重开窗口即丢，`composer-footer` 的「第 n/N 轮」与进度全部归零；更糟的是 **`approvalByThread` 会永久停在 `auto`**（恢复表没了，没人写回原档）。
- `goal-run.ts:152` 的 `stopGoalRun(threadID?: string)` 只判 `undefined`，紧接着 `threadID.trim()`；而 `aside.tsx:144` 的 `startImplement` 传的是 `string | null` 的 `threadID` —— 新会话点「开始执行」直接 `TypeError`。
- `aside.tsx:144` 里 `void writeAgentMode('goal' | 'agent')` 先发（`mode.ts:198` 内部是 `void patchPref`），随后 `aui.composer.send()` —— 模式还没落盘就开跑，注入的可能是上一个模式的 system prompt。
- `goal-run.ts:220` 的 `findGoalSignal()` 只认行首裸写的 `GOAL_DONE` / `GOAL_CONTINUE`；模型写成 `**GOAL_DONE**`、`GOAL_DONE。`、`\`GOAL_DONE\`` 就判不出，`goal-auto-advance.tsx` 会命中 `if (!signal && goal.used > 0)` 分支，把「已完成」误报成「已停」。
- `goal-auto-advance.tsx` 只订阅「最后一条助手正文的 digest」，**不判断这条消息是否属于目标轮次**：用户插一句话、模型答完、正文里没有标记 → 目标被当成「未达成」停掉；反过来用户提问里恰好含 `GOAL_CONTINUE` → 目标被推着乱跑。`runtime.tsx` 又开了 `unstable_enableMessageQueue: true`，排队消息与自动续跑可能抢同一轮（G4）。
- `features/agent/port/model.ts` 在目标模式发送时 `startGoalRun(host.threadID, text.slice(0, 500), ...)`，objective 被截断；`session.ts` 在后台轮次里用 `readApprovalMode()`（当前 UI 线程）而不是 `readApprovalModeFor(threadID)`（G7）。
- `composer-footer.tsx` 的 `第 ${Math.min(run.used + 1, run.budget)}/${run.budget} 轮` 在预算用尽后仍显示「第 6/6 轮」，没有「已用尽 / 已暂停 / 已完成」三态（G11）。

## 方案

### 一、VS Code 实现的调研结论（源码对照）

VS Code 的 Chat 把这些状态**都当成一等数据**，而不是从消息正文里猜：

| 关注点 | VS Code 做法（源码） | 关键细节 | 对本地方案的结论 |
| --- | --- | --- | --- |
| 计划产出 | `vscode_reviewPlan` 工具 + `ChatPlanReviewData`（`builtinTools/reviewPlanTool.ts`、`common/model/chatProgressTypes/chatPlanReviewData.ts`） | 模型把 `title / content / actions / planUri / canProvideFeedback` 交给工具，UI 渲染审批卡片，**工具返回值就是审批结果**（`raceCancellation(reviewData.completion.p)`） | 本地改不了 goose 的工具面，本轮保留「正文解析」，但要先**落成结构化快照**；工具化列为后续（本地等价物 = `parsePlanText` + `PlanRecord`） |
| 计划生命周期状态 | `ChatPlanReviewData.isUsed / isOutdated / draftFeedback / draftCollapsed`，`toJSON()` 只序列化这些可持久化字段 | `dismiss()` 幂等（`if (this.isUsed) return`）；`isUsed` 一旦为真按钮区被 `markUsed()` 清空 | 采纳：`PlanRecord.status` 与 `isUsed` 同构，`revision` 对应 `isOutdated` |
| 计划被改动怎么办 | `chatPlanReviewPart.ts` 的 `watchPlanChanges()`：既监听 `ITextModel.onDidChangeContent`，也建 `IFileService.createWatcher`，任一命中 → `markOutdated()` → 标题栏挂 **Outdated** 徽标并广播 aria status | 不是「重新生成计划」，而是**保留旧计划 + 打过期标记**，让用户自己决定重跑 | 采纳：正文 digest 变化 → `revision + 1` 且 `status` 回落 `draft`，UI 显示「计划已更新，需重新执行」 |
| 计划文件与正文的关系 | `savePlanFile()`：提交前若文件 dirty 先 `save`，再 `updatePlanContentFromModel()` 把**编辑器里的正文**写回 `review.content` 并重渲染 | 文件是唯一真相，卡片只是它的视图；`planUri` 同时用来开「Open Full Plan」 | 采纳：`PlanRecord.body` 与 `.cogito/plans/*.md` 双向绑定，`source: 'file'` 时以文件内容为准 |
| todo / 计划清单持久化 | `ChatTodoListService`（`common/tools/chatTodoListService.ts`）：`new Memento('chat-todo-list', storageService)`，`StorageScope.WORKSPACE` + `StorageTarget.MACHINE`，key = `chatSessionResourceToId(session)`；`setTodos()` 后 fire `onDidUpdateTodos`；另有 `migrateTodoList()` | 按**会话**存、有变更事件、带迁移函数 | 采纳：`planByThread` / `goalByThread` 以 threadID 为键，配 `parseAgent` 白名单 + 迁移/裁剪 |
| todo 的写入协议 | `manage_todo_list`（`builtinTools/manageTodoListTool.ts`）：整份数组覆盖写、`read`/`write` 两种操作、状态枚举 `not-started / in-progress / completed`、渲染 `[x] / [-] / [ ]`、对 <3 项、>10 项、单次改 >3 项给警告、`toolSpecificData.kind = 'todoList'` 交给专用 widget | 清单是**结构化数组**，不是 Markdown | 部分采纳：`PlanRecord.steps` 存结构化数组（现在已从正文抽 `steps`），进度只做 UI，不进 `body` |
| 目标（goal）的表达 | `ChatGoalSummaryService`（`browser/chatGoalSummaryService.ts`）+ `ChatGoalBannerWidget`（`widget/input/chatGoalBannerWidget.ts`） | 小模型把用户 prompt 压成 ≤100 字目标短语（`MAX_PROMPT_CHARS 4000 / MAX_SUMMARY_CHARS 100 / CACHE_SIZE 50`，in-flight 去重，`REFUSAL_PREFIX_RE` 过滤拒答），横幅显示在输入框上方，`setLoading / setGoal / clear / onDismiss` | 采纳：`objective` 不再 `slice(0, 500)`，拆成 `summary`（≤120 字，用于横幅/控制条）+ `detail`（原 prompt，续跑时注入）；无模型的场景退化为「首句截断」 |
| 会话级持久化写法 | `ChatSessionStore`（`common/model/chatSessionStore.ts`） | `maxPersistedSessions = 400`、index 存 `'chat.ChatSessionStore.index'`、`.jsonl` 追加日志、`Sequencer` 串行化写、`onWillShutdown` 里 `e.join(storeTask)` 保证落盘、workspace 切换时迁移会话文件 | 采纳：`plan-store.ts` 内部用防抖串行 flush，并在窗口关闭/切库前**同步排空**内存 cache（Tauri Store 不会自己帮我们 flush） |
| 模式体系与刷新节流 | `chatModes.ts`：builtin `Ask / Edit / Agent`（Agent 受 `AgentEnabled` 策略控制）+ 自定义 agent；自定义模式缓存到 `` `chat.customModes.${sessionType}` ``，`Delayer(100)` 节流刷新，observable 暴露 name/label/icon/model | 模式是**可订阅的服务**，不是埋在组件里的 `void patchPref` | 采纳：`writeAgentMode` 改返回 `Promise` 并 `await`，`startImplement` 串行化；订阅沿用现有 `subscribeAgentMode` |

补充：`planAgentDefaultModel.ts` 只是一条 `DefaultModelContribution`（`filter: metadata.capabilities?.toolCalling`），说明 VS Code 的「计划模式」= **专用默认模型 + 专用工具**，不是纯提示词模式 —— 这也是它天然不需要「从正文猜计划」的原因。

### 二、选定做法

**A（否决）只记 message id**：正文会随会话继续而漂移，指回的消息 id 仍可能被重写，计划本体救不回来。
**B（否决）只存 `.cogito/plans/*.md`**：没有工作区就没有记忆，且 `status / executedAt` 无处安放。
**C（采纳）Tauri Store 存 PlanRecord（`planByThread`）+ 手动/自动导出文件**：唯一真相在应用侧，文件是导出物兼「外部可编辑入口」，用 mtime+digest 判过期。
**D（后续）SQLite 新表**：需要新 IPC 与迁移脚本，收益与 C 相同，等数据量变大再迁。

### 三、数据模型与状态机

```
PlanRecord {
  threadID, title, overview, steps: string[], body,        // body 全文，唯一执行依据
  status: 'draft' | 'running' | 'done' | 'interrupted' | 'superseded',
  source: 'thread' | 'file', filePath?, revision: number,
  digest, createdAt, updatedAt, executedAt?, finishedAt?
}
GoalRecord {
  threadID, summary, detail, budget, used, progress: {done,total} | null,
  status: 'running' | 'paused' | 'done' | 'exhausted',
  approvalBefore: ApprovalMode | null, updatedAt
}
```

- 计划状态迁移：`draft` --点执行--> `running` --GOAL_DONE / 手动标记--> `done`；`running` --abort / error / 用户插话--> `interrupted`；任何状态下 `digest` 变化 → `revision + 1`、`status` 回 `draft` 并标「已更新，需重新执行」（对应 VS Code 的 `isOutdated`）。
- 目标状态迁移：`running` --标记缺失/插话--> `paused`；`used >= budget` → `exhausted`；`GOAL_DONE` → `done`。`approvalBefore` 落盘，刷新后照样能还原审批档（修 G6）。
- 裁剪：`planByThread` / `goalByThread` 按 `updatedAt` 保留最近 200 条、单条 `body` 上限 64 KB（超出截断并置 `truncated: true`，UI 提示「计划过长，建议另存文件」）。

## 实施步骤

1. **persist 层扩字段**：`features/persist/{types,defaults,parse}.ts` 增加 `planByThread` / `goalByThread`（`Record<string, PlanRecord | GoalRecord>`），`parseAgent` 按白名单逐字段校验（`status` 枚举不合法即丢该条，`body` 非字符串即丢），默认值空对象；补 `parse.test.ts` 断言「旧 `agent.json` 无这两个键时读出 `{}`」「脏字段被过滤」。验证：`pnpm --filter @cogito/client exec vitest run src/features/persist/parse.test.ts`。

2. **新建 `features/agent/plan-store.ts`**：内存 cache + `subscribePlan(listener)` + 400 ms 防抖 flush 到 `patchPref('agent')`（写入串行，避免并发覆盖）；导出 `upsertPlan / readPlan(threadID) / markPlanStatus(threadID, status) / bumpPlanRevision(threadID, digest) / prunePlans()`。同时把 `plan-draft.ts` 的正文解析抽成纯函数 `parsePlanText(body): PlanDraft | null` 与 `isPlanDocument(text): boolean`（要求：有 H1 或计划类标题 + `steps.length >= 2`），`findPlanDraft` 改为「`findLastAssistantText` + `parsePlanText`」保持行为不变。验证：新增 `plan-draft.test.ts` 断言「普通问答 → `isPlanDocument` false」「标准计划骨架 → true 且 steps 为实施步骤」。

3. **新增常驻 `views/agent/chat/components/plan-recorder.tsx`，挂到 `chat.tsx`**：`useAuiState` 取最后一条 assistant 正文 → `parsePlanText` → 与档案 `digest` 比对：新增则 `upsertPlan({status:'draft'})`；内容变则 `bumpPlanRevision` 并把 `running → draft`；无计划则不动档（**绝不删除**）。目标模式同一处把 `summary/detail` 写进 `GoalRecord`。验证：手工「计划 → 再发 3 轮问答」，右栏计划不消失、`revision` 不变；手改计划文件后 `revision + 1`。

4. **`aside-plan.tsx` 改读档案**：内容取 `readPlan(mainThreadID) ?? findPlanDraft(messages)`（旧会话兼容）；抬头加状态徽标（草稿/执行中/已完成/已中断/已更新）与「保存路径」；底部按钮去掉 `props.isPlanMode` 包裹，改为「档案存在即可见」，并新增「标记完成 / 重新执行 / 从文件载入」。验证：切到 agent 模式后按钮仍在；点「标记完成」徽标变「已完成」且刷新后保持。

5. **`aside-busy.tsx` 与 `chat.tsx` 的自动展开统一走档案**：`PlanDraftBlock` 改读 `readPlan(threadID)`（`plan.entries` 有值时不覆盖，保持现有优先级）；`PlanAutoOpen` 的 `planTotal` 改成「档案 steps 数或 status 变化」触发一次展开。验证：计划产出后右栏自动展开一次；后续消息不再反复抢占用户手动关闭的状态。

6. **`aside.tsx` 的 `startImplement` 串行化改造**：`const record = readPlan(threadID) ?? draft`；`await writeAgentMode(target === 'goal' ? 'goal' : 'agent')` 后再 `stopGoalRun(threadID ?? undefined)`（修 `stopGoalRun(null)` 抛错）再 `aui.composer.send()`；发送前 `markPlanStatus(threadID, 'running')`，`buildPlanExecutePrompt` 增加可选 `filePath` 与 `revision` 行，正文仍取 `record.body`（无档案才回退 `draft.body`）。验证：新会话直接点「开始执行」不抛错；抓 composer 文本确认是档案全量正文。

7. **`goal-run.ts` 持久化 + 状态机 + 信号归一化**：`runs` / `approvalToRestore` 改为读写 `GoalRecord`（`subscribeGoalRun` 保留，内部订阅 `plan-store` 的同一套 cache）；`stopGoalRun` 对 `null`/空串都 no-op；`findGoalSignal` 先归一化（去 `* _ ` \` 引号、转大写、允许行内出现）再匹配，`GOAL_DONE` 优先；`goal-auto-advance.tsx` 增加归属判断（本轮 composer 文本必须等于上一次续跑/首轮提示，或 `GoalRecord.used` 与消息数匹配）与「队列非空不发」（读 `composer.getState()` + runtime 的 queue 状态），命中即 `paused` 并提示。验证：`goal-run.test.ts` 补 `findGoalSignal('**GOAL_DONE**') === 'done'`、`stopGoalRun(null)` 不抛、`used/budget` 三态。

8. **`plan-file.ts` 补 `listPlanFiles / readPlanFile`**：`readDir(join(rootPath, '.cogito/plans'), { isHiddenVisible: true })` 过滤 `.md` 并按 mtime 倒序，`readTextFile` 回读（剥 frontmatter → `body`，`name`/`overview` 回填），保存改名为 `<slug>.md` 覆盖写（保留时间戳仅作首次）；`aside-plan.tsx` 增「从文件载入」列表，载入后 `upsertPlan({source:'file', filePath})` 并可一键执行。同步更新 `docs/apps/client/plan-mode.md`（状态机、「清单不落盘、正文唯一」不变）。验证：`plan-file.test.ts` 补 `list` 排序与 `read` 还原断言；手工从文件载入后执行，抓取发送文本 = 文件正文。

## 风险与待确认

- **误判「新计划」**：任何含两条编号列表的回复都可能被 `isPlanDocument` 判成计划。缓解：要求 `steps >= 2` **且**（有 H1 计划标题 **或** 命中「实施步骤/方案/计划」标题）；`revision` 变化只打标记，不覆盖 `status: 'done'`（已完成计划被新问答污染时宁可提示，不可静默回滚）。
- **档案与消息双源冲突**：旧会话没有档案、新会话两者都有。规则定为「档案优先，档案缺失才回退 `findPlanDraft`」；需确认是否要给档案加 `migrated: true` 以免重复回填。
- **`body` 体积**：计划正文动辄 4–8 KB，200 条上限下 `agent.json` 可能到 MB 级。待确认是否降到 50 条 + 更激进截断（截断会破坏「正文唯一依据」，需产品决策）。
- **审批档还原的副作用**：刷新后 `approvalBefore` 若为 `auto` 则保持，若为 `ask` 则用户可能在无人值守时被审批卡住；建议刷新后把 `running` 的 GoalRecord 一律降级为 `paused`，等用户点「继续」再恢复，避免「后台静默自动放行」（当前 `session.ts` 在目标推进期间直接 `pickAutoAllowOption` 已是高风险点，G7 一并修）。
- **排队消息 vs 自动续跑**：`unstable_enableMessageQueue: true` 下两条路径都可能写 composer；本轮只做「队列非空不发」的防守，是否关掉 message queue 需确认是否影响普通体验。
- **不引入 VS Code 式工具面**：`vscode_reviewPlan` 的价值在于「结构化 + 审批回传」，本地要等价实现需在 goose 侧注册工具与 data part，超出本次改动边界；列为后续项（届时 `PlanRecord` 可直接作为工具的落地形态）。
